## 二、⚠️ 为什么容易误判为「未填」——两个陷阱

**陷阱 1：判定位的写法是「数字写在横线内」**，不是替换横线。
决策方的实际写法是 `` `_0__` ``、`` `__0_` ``（保留下划线、把数字填在其中），
**不是** `` `0` ``。因此：
- 用 `grep -c '`0`'` 或正则 `` `([012?])` `` 去找**恰好一个数字** → **命中 0 次** → 误判为「未填」；
- 正确判据是「反引号内含**恰好一个** `0/1/2`」，例如：
  ```bash
  grep -oP '判定（决策方填）\*\*：`[^`]*`' docs/gold_set/answer_sheet_s5_control.md \
    | grep -c '[012]'      # 期望 50
  ```
  （执行方的解析器早已适配：`rulings_io.slot_value()`，见 `rulings_io.py` 自测第 1 条。）

**陷阱 2：这两份文件的提交尚未推送。** `013e18b`、`6fac2c3` 均为**本地提交**；
按决策方 2026-10-02 定的纪律 R29（**推送每天一次**，因网络不稳定），远端目前停在 `5f7288f`。
因此**任何通过 GitHub raw / GitCode 网页读到的版本都不含 S5**（文件不存在或为空）。
→ **读本地路径**，或要求执行方提前推送（见 §四）。
