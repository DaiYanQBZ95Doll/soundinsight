## 二、本轮新增发现

### A. M8 的"24 小时复查"落在截止之后，不具备补救能力

M8 规定：提交安排在 10/8 上午 → 提交后 **30 min 内确认** → **24 h 后复查**。24 h 复查的时点已在 **10/8 截止之后**。若复查发现问题，异常预案中的"用剩余次数重传"受截止约束，实际已不可执行。**唯一具备补救能力的窗口是提交后那 30 分钟**；24 h 复查的定位只能是事后追溯记录，这一点在清单中未区分。

### B. 日历前移后，数字窗口的关键路径不是 GPU 型

D17 把数字窗口压到 **10/1–10/3（3 天）**、冻结提前到 10/4。A-必做中的数字类包共 11 个（W1、W2、W3、W4、W5、W6、W7、W14、W15、W16、W17）。按依赖列展开，关键路径为：

```
P0-3（字段恢复） → W4（四五星开采 + 人侧抽检 30–60 min）
                 → W5（重训 + 阈值扫描 + 5 折 CV）
                 → W16（星级分层归因一致性）
```

清单给出的可行性依据是"执行方实测单折 125 s/epoch、5 折 CV ≈49 min"，即**训练速度**。但关键路径上的 **W4 是 API 调用 + 人工抽检等待型**（时间盒 1 天，且触发人侧节点），W1（四方案对比）也是多轮训练 + 评估。**训练速度不构成 W4 与 W1 的可行性依据**——压缩窗口的瓶颈在这两包，而非 W5。

### C. §九 A 类（人工必改清单）与 E4（机械覆盖清单）不一致

E4 声明的纳入对象是 6 份：执行依据、质检方并行版、缺憾清单、外部来源登记、本清单、锁定前审计。而 §九 A 类已列 `gap_and_roadmap_inventory.md`，**未列** `docs/final_project_review_and_execution_plan.md`。实测该总纲含 v1 数字 **9 处**（`0.6871` ×3、`0.9744` ×5、`0.6241` ×1），属必须同步的文件；`docs/pre_lock_completeness_audit.md` 实测含 0 处 v1 数字，无需数字同步。故两份清单对"总纲"的处理存在缺口（E4 执行后由机械检查兜住，但 A 类人工清单本身不完整）。

### D. `check_doc_numbers.py` 的覆盖补全（E4）**当前尚未落地**

实测 `PAIR_FILES` 仍为原 10 项（`competition_v4.md`、`competition_v3.txt`、`README.md`、`QWEN_HANDOFF.md`、`MODEL_CARD.md`、`AI_HANDOFF/01`、`AI_HANDOFF/03`、`docs/retrospective_and_reflection.md`、`docs/finals_stage.md`、`docs/v2_acceptance_benchmark.md`），`GEN_FILES` 仍为 `PAIR_FILES + docs/project_full_record.md + PROGRESS_SYNC.md`。§七 所称"实测纳入 6 份后 0 FAIL"属**试跑结论**，尚未写回工具。E4 作为 A-必做项，其完成判据（纳入并 0 FAIL）目前未满足——这符合"待执行"状态，但需注意：**在 E4 落地前，总纲等文档的编辑不受代际与配对检查约束**。
