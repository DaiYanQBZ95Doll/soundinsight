## 第一部分：接下来怎么推进

### 1.1 已闭合 vs 未闭合（避免重复讨论）

**已闭合**（无需再议）：三轮红队质询的全部 spike、口径成对、孤儿文件、项数/体积声明一致性、
单条推理语种过滤缺口、语种边界精确化、token 预算、240 元来源标注、M8 的 24h 复查处置。

**未闭合**（唯一需要人侧动作的一组）：

| ID | 事项 | 谁 | 代价 | 不做的后果 |
|---|---|---|---|---|
| **G-1** | **人工金标 300 条盲评** | 决策方或队友 | 1.5–3 h（拆三层后各约 40 min） | 所有 LLM 口径数字**永久**带"未经校准"；红队三轮质询的共同落点 |
| **D-Q2** | treble 评测分辨率（该类测试正例仅 10 条） | 决策方拍板 | 0.1 h 决策 + 执行方 1 h | 最弱类的任何改进**测不出来** |
| **D-Q3** | V1.6 更正提案落地（W11 加注／outside_gate_fp 加前提／附录 B 标 LLM 口径） | 决策方 | 0.1 h | 材料里仍引用已被推翻的结论 |
| **D-Q4** | 视频是否重录 | 决策方 | 0–4 h | 包内已写口径说明，风险可控 |
| **D-Q5** | M1 主文档人工复核 | 决策方或红队代读 | 0.3–2 h | 提交前少一道人眼 |
| **M8** | 10/8 正式提交 | **只能决策方** | 0.5 h | 目标终点条件 |

### 1.2 三条推进路线（战略层，供选择）

| 路线 | 内容 | 上行 | 代价 |
|---|---|---|---|
| **A 打满 10/8** | A1 评审导读一页纸（执行方起草，决策方过目）＋ A2 路演 PPT 骨架（若进 6 强） | 直接决定"材料被读懂的比例" | 决策方 0.2 h |
| **B 方法资产化** | B1 技术写作《我们量了自己的盲区》＋ B2 开源验证模板＋ B3 决策队列工作法 | 把方法变成可带走的东西（目前一分未变现） | 决策方润色 1–2 h |
| **C 变成真东西** | C1 **找 1 个真实卖家聊 30 分钟**；C2 品类扩张（$3 + 1 天/新品类）；C3 定位选择 | 修掉"无真实用户验证"这个根本弱点 | **只能决策方**（约 0.5 h 起） |

## 第二部分：如何保证原有功能不出问题（**本议程的重点**）

### 2.1 现有防护（已机械化的，逐条可复跑）

| 防护 | 覆盖什么 | 复跑 |
|---|---|---|
| 15 步门槛链 | 审计 → 自测 → 断链/依赖 → URL → 换代 → 打包 → 哈希 → 包内校验 → **端到端实跑** → **产品入口(UI/API)** → **存活巡检** → 状态卡 → 快照 → manifest → 卫生 | `python run_all_checks.py` |
| 数字审计（242 项） | 阈值成对、代际标签、口径成对总量、清单版本、体积声明、项数声明、模板合规、v2 产物、**产品代码健康**、**语种过滤覆盖** 等 | `python check_doc_numbers.py` |
| 负向自测（31 项） | 证明上述检查**会拒绝坏输入**（而非只报 PASS） | `python test_audit_checks.py` |
| 冻结校验 | 阈值文件/模型哈希登记、**红线 9**（复赛包构建前后双向哈希） | 打包步骤内置 |
| 包内校验 | 内层哈希一致 + Demo 冒烟 + **解包实跑出七节报告** | `verify_finals_package.py` / `verify_demo_end_to_end.py` |
| 产品入口验证 | Gradio UI 起服 200、API `/health` 与 `POST /predict` 200 且判定正确 | `verify_ui_and_api.py` |
| 语种过滤覆盖（新增） | 凡**调用**模型的函数必须过滤或委托核心 | 审计内 |
| 预提交守卫 | 凭据模式／敏感文件名／超大文件 | `safe_commit.py` |

### 2.2 **尚未防护的缺口**（执行方自查，红队可补充/反驳）

| # | 缺口 | 后果 | 建议防护（执行方工作量） | 优先级 |
|---|---|---|---|---|
| **P1** | **无金标输出回归测试**——样例报告只检"节数=7"，不检内容/数字/措辞；重构后报告可能悄悄变样 | 产品输出的静默漂移（评委看到的是变了样的报告） | 为样例报告做**快照断言**（关键字段 + 结构 + 字数区间），纳入门槛链（1 h） | **高** |
| **P2** | **两个 UI 文件是近重复实现**（`demo_sound_v2.py` 与 `deployment/app.py`），靠人工同步 | 改一处忘另一处（**单条过滤缺口就是这样产生的**） | 加**行为一致性检查**（AST 比对各 UI 回调的函数名与过滤调用），或抽公共模块（2 h） | **高** |
| **P3** | **UI 交互路径只验了"服务能起"，未验"点了能用"**（如批量上传、下载按钮、第三页边界案例） | 评委点某个按钮才发现问题 | 用**无头调用**直接调用回调函数（`batch_analyze` 传入样例 CSV、`single_predict` 已验），纳入门槛链（1–2 h） | **高** |
| **P4** | **API 错误路径未测**（空 `texts`／超长／非 JSON） | 422/500 行为未知，评委可能撞上 | 补 4 条契约测试（0.5 h） | 中 |
| **P5** | **数据文件缺失时检查静默 SKIP**（如 `review_meta_v2.csv` 不在则跳过） | 检查"看起来全绿"其实没跑 | 把关键 SKIP 改为 FAIL 或打印醒目提示（0.5 h） | 中 |
| **P6** | **冻结靠纪律+哈希，不靠权限** | 误操作可覆盖冻结件（事后能发现，但不能复原） | 加"冻结件只读副本 + 每次链首校验"（0.5 h） | 中 |
| **P7** | **无 CI**——全部检查靠人记得跑 | 忘记跑就无信号 | 提供 `run_all_checks.py --fast`（跳卫生与打包，约 30 s）供高频使用（0.5 h） | 中 |
| **P8** | **第三方无法复算**（权重不入库，只有哈希+命令） | 评委/红队只能核对哈希，不能独立验证指标 | 已声明为**策略选择**（hash_and_command_only）；若要改需决策方定分发方式 | 低（决策项） |

### 2.3 建议的落地顺序（若批准）

1. **P1 + P3**（当天可完成）——它们直接保护"评委看到的东西"；
2. **P2**（抽公共模块或加一致性检查）——它正是本次缺口的根因；
3. **P4 + P5 + P7**（半天）——补上契约、SKIP 语义与快速模式；
4. **P6**（半天）——冻结件的物理防护；
5. **P8** 留作决策项。

### 2.4 需要回答的问题

1. 上述 P1–P8 是否批准执行？（P1–P3 建议无条件批准；P4–P7 视时间）
2. 红队是否认同/补充这份缺口清单？（**欢迎直接反驳**——尤其 P1/P2/P3 的优先级）
3. 是否有"必须不能坏"的清单需要单独加固？（例如：`config.json` 路径、`download_models.py` 链接、报告七节结构）
